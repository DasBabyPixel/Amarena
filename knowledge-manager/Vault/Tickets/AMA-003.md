# Problem

Wie werden Game Stages in Amarena an FTB-Quests gekoppelt, damit ein Quest-Abschluss Items freischaltet? Welche Felder braucht der Reward in der Kapitel-SNBT, und werden Stages fuer bereits abgeschlossene Quests nachtraeglich vergeben?

# Lösung

Entscheidung vom 2026-09-20 (Nutzer hat zwischen den Varianten gewaehlt): Jede Quest des Kapitels Wooden Age (config/ftbquests/quests/chapters/stone_age.snbt) vergibt ihren Stage ueber einen FTB-Quests-Reward vom Typ gamestage direkt in der SNBT: rewards-Liste mit den Feldern auto: invisible, id (16-stellige Hex-ID, erste Ziffer 0 bis 7, im ganzen Questbuch eindeutig), stage: Stage-Name, type: gamestage - Schluessel alphabetisch, Tabs, direkt nach der id-Zeile der Quest. auto: invisible muss explizit in der Datei stehen: im Editor ist invisible zwar der Default fuer Stage-Rewards, beim Lesen aus der Datei bedeutet ein fehlendes auto aber default, und der Reward muesste manuell abgeholt werden. Wirkungskette: Pixels GameStages ersetzt die KubeJS-Player-Stages durch einen eigenen Wrapper (KJSStagesWrapper), FTB XMod Compat waehlt bei geladenem KubeJS automatisch KubeJS Stages als Provider (Logzeile Chose [KubeJS Stages] as the active game stages implementation), der gamestage-Reward landet damit im Stage-System der Mod. Stages werden pro FTB-Team gespeichert. FTB Quests prueft bei jedem Login alle abgeschlossenen Quests erneut auf Auto-Claim-Rewards (ServerQuestFile.checkQuestBookOnLogin ruft TeamData.checkAutoCompletion), spaeter hinzugefuegte Rewards werden also nachtraeglich vergeben. Manuell testen mit /kubejs stages add, remove, list oder clear plus Spielername. Inhaltliche Festlegungen: der Ofen wird ueber den Stage der Oak-Crucible-Quest craftbar, weil die Clay-Quest eine Glasflasche braucht; die letzte Quest (Andesite, progress to the next age) hat bewusst noch keinen Reward. Alternativen: (A) gamestage-Reward in der SNBT, gewaehlt - pro: die Kopplung steht sichtbar an der Quest, kein Skript noetig, nachtraegliche Vergabe beim Login inklusive; contra: FTB schreibt alle Kapiteldateien bei jeder Editor-Aenderung neu, Hand-Edits muessen deshalb in Repo UND Instanz landen und per /ftbquests reload geladen werden, bevor im Spiel weiter editiert wird. (B) KubeJS-Skript auf das Quest-Abschluss-Event, das den Stage per Quest-ID vergibt - pro: Quest-Dateien bleiben unberuehrt; contra: zweite Zuordnungstabelle Quest-ID auf Stage, die bei Quest-Aenderungen still veraltet, und die nachtraegliche Vergabe muesste selbst gebaut werden.
